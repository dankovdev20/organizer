# Решения по проекту

Формат: решение → почему → цена/альтернатива.

## Архитектура

1. **Данные хранятся локально в браузере (IndexedDB), Supabase — синхронизация и бэкап.**
   Приложение работает офлайн (метро, подвал), отвечает мгновенно без сети и не требует аккаунта. Supabase нужен для бэкапа: Safari может очищать данные сайтов, и облачная копия защищает от их потери, а также даёт синхронизацию между устройствами.

2. **Приложением можно пользоваться без входа в аккаунт.**
   Обязательный вход при первом запуске шёл бы против идеи «открыл → записал → вышел». Трат за день может быть много, каждая должна добавляться за секунды.

3. **Отдельного бэкенда (DRF, Express, свой API) нет — бэкенд это Supabase.**
   Supabase закрывает всю серверную часть: схема PostgreSQL в миграциях, Row Level Security (каждый видит только свои данные), Edge Functions для серверного кода (push, секреты), pg_cron для задач по расписанию, тесты базы на pgTAP. Отдельный API при local-first был бы лишней прослойкой между клиентом и базой. Если понадобится серверная логика — добавлю на TypeScript (Edge Functions или Route Handlers Next.js).

4. **PWA, а не нативное приложение или React Native.**
   Одна кодовая база на моём веб-стеке (Next.js, TypeScript), установка прямо из браузера, не нужны App Store и Apple Developer Program. Цена: ограничения iOS — push работает только в установленной на экран «Домой» PWA начиная с iOS 16.4, Safari может очищать хранилище.

## Синхронизация

5. **UUID генерируется на клиенте (`crypto.randomUUID()`), а не базой.**
   Запись получает постоянный id сразу, даже офлайн, без запроса к серверу. Id, созданные на разных устройствах, не пересекаются, поэтому записи можно безопасно сливать при синхронизации.

6. **Мягкое удаление (`deletedAt`) вместо физического.**
   Чтобы при синхронизации удалённые данные не вернулись обратно с сервера: `deletedAt` работает как флаг, что запись удалена и восстанавливать её не нужно. При физическом удалении синхронизатор не отличит «удалили» от «ещё не было».

7. **Конфликты: last-write-wins по `updatedAt`.**
   Если одну запись изменили на двух устройствах, остаётся версия с более поздним `updatedAt`. Это самая простая стратегия. Слабые места: правка «проигравшего» устройства теряется без предупреждения; если часы на устройстве идут неправильно, старая версия может оказаться «новее». Для личного трекера с одним пользователем это приемлемо.

8. **При выходе из аккаунта локальные данные стираются.**
   Чтобы приложением можно было пользоваться и на чужом устройстве: зашёл в свой аккаунт, данные подтянулись из облака, добавил запись, она ушла в облако, вышел — на устройстве не осталось следов. Если есть неотправленные изменения, перед выходом показывается предупреждение и кнопка «Синхронизировать сейчас».

## Деньги

9. **Суммы хранятся целыми числами в минимальных единицах (гроши/центы), не float.**
   У float всегда есть погрешность (`0.1 + 0.2 !== 0.3`), а при постоянном суммировании трат она быстро накапливается.

10. **У траты хранится снимок курса на момент траты.**
    Чтобы при изменении курса не менялись прошлые траты: 10 zł сегодня — это одна сумма в UAH, завтра другая. Общая сумма трат за прошлые периоды не должна «плыть» вместе с курсом.

11. **Курсы статичные (константы в коде, обновляются вручную).**
    Это упрощение для MVP; внешний API (NBP) — после основного функционала. Последствие: курсы устаревают, и новые траты в валюте считаются по неточному курсу. Что смягчает: снимок курса (прошлые траты не меняются) и единая функция получения курса — для перехода на API меняется только она.

12. **Сумма в PLN хранится отдельным полем, а не вычисляется каждый раз.**
    Статистика складывает одно готовое поле (`SUM(amount_pln)`) и в IndexedDB, и в Postgres, а округление при конвертации происходит один раз при сохранении. Цена: поле нужно пересчитывать при каждой правке суммы или валюты.

## Модель данных

13. **Категории — константа в коде, а не таблица в базе.**
    Пользователь не создаёт свои категории, набор фиксированный — значит, таблица и её синхронизация не нужны, а тип `CategoryKey` выводится прямо из константы. Цена: изменить набор категорий можно только новым деплоем.

14. **У категории отдельно ключ и отдельно название.**
    Ключ (`'food'`) хранится в базе и никогда не меняется. Название («Еда») — только текст для UI: его можно переименовать или перевести без миграции данных.

15. **Локация — объект `{ lat, lng } | null`, а не два nullable-поля.**
    Чтобы нельзя было оставить одно из двух полей пустым, а была только возможность пропустить шаг целиком. Принцип: невалидные состояния не должны быть представимы в типах.

16. **Даты хранятся ISO-строками в UTC (`toISOString()`).**
    UTC убирает путаницу с часовыми поясами (полночь по Варшаве — ещё вчера в UTC). Единый формат позволяет сравнивать и сортировать даты как строки. Строка без преобразований проходит через JSON и ложится в `timestamptz` в Postgres. Для отображения дата форматируется на фронте.

## Авторизация

17. **Вход по паролю; код на почту — только при регистрации и восстановлении пароля.**
    Вход по коду (OTP/magic link) отправляет письмо при каждом входе, вход по паролю — ни одного. При лимитах SMTP (у встроенного почтового сервиса Supabase — 2 письма в час на проект) это заметная экономия. Альтернатива «только код» короче для пользователя, но сильнее упирается в лимиты.

18. **В разработке — локальный Supabase (CLI), а не облачный.**
    Письма перехватывает Mailpit, лимитов на отправку нет, боевые данные не затрагиваются, а окружение воспроизводится из миграций в репозитории. Для публичного демо всё равно нужен свой SMTP (например, Resend).

19. **Пока без Sign in with Apple.**
    Нужен аккаунт Apple Developer Program, а для веба Apple требует перевыпускать секретный ключ каждые 6 месяцев. На этапе MVP хватает Google и GitHub.

## UX

20. **Ввод траты пошаговый, по одному полю за раз.**
    Для простоты пользователя: его ведут за руку, UI не выглядит пугающим и перегруженным. Для подхода «зашёл → добавил → вышел» это лучший вариант. Обязательны только сумма и название, остальные шаги можно пропустить.

21. **Нет бургер-меню, навигация через таб-бар.**
    Бургер рядом с таб-баром — это две навигации на одном экране; пункты, спрятанные в бургере, плохо находят. Apple в Human Interface Guidelines называет таб-бар основной навигацией iOS. Профиль — иконка в шапке, потому что его открывают редко.

22. **«Потратили на X% больше» сравнивается с тем же отрезком прошлого периода.**
    Если прошла только часть месяца, сравнение со всем прошлым месяцем нечестное (весь октябрь против двух недель ноября) — проценты считались бы неправильно. Текст показывается, только если есть с чем сравнивать.
